2.1 Theoretical Background

2.1.1 Data-Instruction Separation and Semantic Equivalence

(Existing section retained.) SQL injection and cross-site scripting both happen when the boundary between user-supplied data and executable instructions is not preserved [21], [73]. Because the same intent can be written in many ways — different encodings, comments, spacing, and broken-up keywords — detection cannot rely on matching one familiar string [22], [23].

2.1.2 Building a Web-Attack Corpus and Payload Obfuscation

The method in Chapter 3 does not use raw benchmark strings directly. It builds a labelled dataset in which each attack is produced by a family-specific generator (for SQL injection: tautology, UNION-based, boolean-blind, time-based blind, error-based, stacked-query, and authentication-bypass; for cross-site scripting: reflected, stored, and DOM-based [22], [23]), and each attack can then be obfuscated by encoding, comments, spacing, and case changes. This choice is based on a clear finding in the literature: a model trained only on plain payloads does much worse when it meets changed versions of the same attack, and improves once altered examples are included in training [60]. Building the dataset from documented families, with every payload kept unique, makes the training data cover the range of shapes a detector must handle instead of a few memorable strings. Treating a changed payload as the same attack follows from Section 2.1.1: an attack is defined by the instruction it hides in the data, not by how it looks on the surface [73].

2.1.3 Supervised Learning and Generalization

(Existing 2.1.2, renumbered.) A supervised classifier learns to map labelled examples to categories, and its real value is how well it works on new inputs, not how well it fits the training set [24]. The way the data is represented decides what patterns the model can learn.

2.1.4 Random Forest Classification

(Existing 2.1.3, renumbered.) A Random Forest combines many decision trees, each trained on a random sample of the data and a random subset of the features, so no single tree controls the result [25], [26]. It handles non-linear relationships among mixed numeric and yes/no features well and is available as a standard library implementation [46]. Recent web-attack studies continue to use Random Forest as a strong feature-based detector, often paired with character-level n-gram features [84], [87].

2.1.5 Long Short-Term Memory Networks

(Existing 2.1.4, renumbered.) An LSTM network uses gated memory to keep track of order across a sequence, which lets it remember how characters, delimiters, and broken-up keywords relate to each other across a single payload [19], [47]. Sequence models of this kind, including LSTM variants, are widely used for web-attack and zero-day detection in recent work [83], [86].

2.1.6 Character-Level Tokenization and Padding

The LSTM branch in Chapter 3 does not read words or engineered features; it reads a sequence of characters turned into numbers. Each payload is mapped character by character to a small fixed set of tokens, then padded or cut to 200 positions so every input is the same length. Two things about this matter for the build. First, working at the character level avoids the “unknown word” problem that word-based methods hit on obfuscated payloads, where attackers break tokens apart on purpose; every character has a known token [74]. Second, because most payloads are much shorter than 200 characters, most positions are empty padding, so the network must be told to ignore them; a masking step does this, and without it the model does not learn [79]. These choices are the basis for the tokenization and masking steps in Sections 3.3.2 and 3.7.

2.1.7 Stacked Generalization

(Existing 2.1.5, renumbered.) Stacking combines the outputs of several base models using a second model on top [29]. It only helps when the base models make different, useful mistakes, which is why an ablation is needed to check whether stacking actually adds value over the best single model. Recent studies apply stacked and pooled ensembles to SQL injection and XSS detection and report strong results, while also using stratified training to handle class imbalance [83], [85], [87].

2.1.8 Evaluation Metrics and Statistical Comparison

(Existing 2.1.6, renumbered.) Detection is measured with Precision, Recall, F1-Score, False Positive Rate, and the area under the ROC curve [30], [31], [51]. Since one test set is just one sample, bootstrap resampling gives confidence intervals [32], [52], and McNemar’s test checks whether the differences between two systems on the same records are real rather than chance [33], [53].

2.1.9 Human-Governed Cybersecurity Detection

(Existing 2.1.7, renumbered.) A model like this supports a human decision; it does not, on its own, prove that an attack worked, block traffic, or replace a security analyst [34].

2.2 Technical Background

2.2.1 Web Application Firewalls, ModSecurity, and the OWASP Core Rule Set

(Existing section retained.) ModSecurity with the OWASP Core Rule Set is a rule-based web application firewall. Its work includes input transformations, rule matching, anomaly scoring, paranoia levels, thresholds, exclusions, and audit logging, and its behaviour depends on how it is configured, so any comparison must use one fixed, fully documented setup [35], [36], [37].

2.2.2 Anomaly Scoring, Paranoia Levels, and the Blocking Threshold

The comparison in Chapter 3 treats ModSecurity as a scoring system, not an exact-string matcher, and this needs to be understood to read the baseline results. Under the Core Rule Set, each matched rule adds a weighted amount to a running anomaly score, and a request is blocked only when that score reaches a set threshold [75]. The paranoia level controls how strict the rules are: a higher level turns on more, broader rules that catch more attacks but also flag more ordinary traffic that happens to look suspicious [76]. Chapter 3 fixes the setup at Paranoia Level 2 with a threshold of five, a documented and practical baseline. This scoring-and-threshold behaviour is what explains, in Chapter 4, why a firewall tuned to catch changed attacks can also block a large share of legitimate traffic.

2.2.3 Honeypots and Honeypot-Based Traffic Datasets

A honeypot is a decoy system that records attacker activity, giving traffic that is labelled by how it was collected [43]. The dataset in Chapter 3 is built from WEB-IDS23 flow records with family-based payloads added, producing a labelled log. The usefulness of such a dataset depends on where it comes from, whether it is valid and varied, and whether it is free of giveaways a model could exploit — such as a tool-specific user-agent that would trivially separate attack from benign traffic. Cordero et al. show that synthetic attack data can make controlled, repeatable datasets as long as these issues are checked [45]. The build in Chapter 3 keeps every payload unique and varies incidental fields for exactly this reason.

2.2.4 Technical Architecture of AI-GIS

(Existing section retained; described in full in Section 3.3.) AI-GIS has three parts: a Random Forest branch over engineered features, an LSTM branch over character sequences, and a logistic regression meta-learner that combines their outputs [29], [69], [70].

2.2.5 Feature Engineering and Preprocessing

(Existing section retained.) Each request is decoded and cleaned in the same way before features are taken, so training and testing see the same kind of input.

2.2.6 Model Optimization and Class Balancing

(Existing section retained.) Settings are chosen by cross-validated F1-Score, and the training data is balanced so the model is not biased toward the larger class [49], [50].

2.2.7 Evaluation and Reproducibility Tools

(Existing section retained.) Metrics come from standard library functions [51]; resampling and paired tests measure uncertainty [52], [53]; and a fixed random seed with a recorded environment supports reproducibility [67], [68].

2.4.6 Recent Studies Supporting the AI-GIS Techniques

A number of recent studies support the specific techniques used in this study and place AI-GIS within an active line of research. This subsection groups them by the design choice each one justifies.

Honeypot data for detection. Recent work continues to show that honeypot-collected traffic is a practical source of labelled attack data for machine-learning detection. A 2025 study on honeypot-driven intrusion detection reports that models trained on honeypot telemetry can distinguish malicious from normal behaviour at kernel and network level [82]. Broad surveys of machine-learning intrusion detection [81] and of network-intrusion datasets [89] both stress that dataset provenance, balance, and freedom from giveaways strongly affect reported results — the same concerns the corpus construction in Section 3.2 controls for. These studies support the decision to train on a labelled honeypot-based corpus rather than on isolated payload strings alone.

Character-level features for obfuscated payloads. Several studies confirm that character-level representations capture the structure of obfuscated web attacks better than word-level ones. Work on web-attack detection using character-level n-gram features reports that character n-grams outperform word n-grams because they capture the structural patterns of complex and obfuscated payloads [84]. This directly supports the character n-gram component of the Random Forest feature vector (Section 3.3.1) and the character-sequence LSTM branch (Section 3.3.2), both of which read the payload at the character level for exactly this reason.

Ensembles combining feature-based and sequence-based models. Recent studies combine complementary model types in the same way AI-GIS does. A 2025 study detects zero-day web attacks with an ensemble of LSTM, GRU, and stacked autoencoders, showing that sequence models can be pooled to generalise to unseen attacks [83]. Trustworthy ensemble and boosting models for SQL injection, using stratified training to handle class imbalance and local explanation techniques, report accuracy in the high-nineties [87], and an uncertainty-aware ensemble deep-kernel model for web-attack detection makes the case that combining models improves reliability, not only accuracy [85]. These studies justify both the stacked design (Section 3.3.3) and the ablation that tests whether the combination actually helps (Section 3.8), consistent with the caution that a more complex model is not always better [57].

Neural and NLP-based web-attack detection. Two further studies place the sequence branch in context. A cascaded natural-language-processing approach to SQL injection detection targets high-speed environments and reports strong results, showing that language-model-style processing of payload text is effective [86], and a 2024 study introduces enhanced neural architectures for precision web-attack detection, reporting improvements over prior neural baselines [88]. A 2025 comprehensive review of machine-learning models in web applications situates these methods within the wider field and notes that reported accuracies commonly fall between 93% and 99.9% across recent SQLi and XSS detection studies, which frames the results reported in Chapter 4 against comparable work [90].

Positioning of AI-GIS. Taken together, these studies confirm that each individual technique used by AI-GIS — honeypot-based training data, character-level features, and stacked ensembles of complementary models — is well supported by recent literature. What remains distinctive, and forms the research gap restated in the synthesis below, is the combination of these techniques into one reproducible benchmark that also includes a direct, statistically tested comparison against a fixed rule-based firewall.

2.5 Synthesis

The reviewed work shows that SQL injection and cross-site scripting come from a failure to keep data and instructions apart, and that the same attack can be written in many forms. This leads to two choices in the present method: building a training set that covers documented attack families and their changed versions (Section 2.1.2), not just a few plain strings, and describing each payload in more than one way so that no single view has to catch everything [60].

In line with this, the theory supports looking at payloads two ways at once. A Random Forest sums up measurable properties as features [25], while a character-level LSTM keeps the order of characters and fragments using fixed-length padding and masking (Section 2.1.6) [19], [79]. Studies confirm both views can support web-attack detection, but they also warn that a more complex model is not always better: in at least one study a plain Random Forest matched or beat larger ensembles [57], [58], [59]. This is exactly why the method in Chapter 3 includes an ablation that compares the full model against its parts rather than assuming the combination wins [29].

On the baseline side, the review shows that a rule-based firewall must be understood as a scoring system whose behaviour depends on its configuration (Section 2.2.2), which is why Chapter 3 fixes one documented ModSecurity setup at Paranoia Level 2 [37], [76]. The honeypot-based dataset (Section 2.2.3) provides labelled traffic across the attack families of interest, with checks against giveaways [45].

The gap, then, is not the lack of machine-learning detection, firewall evaluation, or hybrid models as separate topics, each of which exists. The gap is the lack of one repeatable benchmark that puts together a feature-based Random Forest branch, a character-level LSTM branch over the same payloads, a validation-based stacked meta-learner, a labelled honeypot-based dataset, a held-out obfuscated attack benchmark, and a direct, statistically tested comparison against a fixed ModSecurity setup. AI-GIS addresses this gap through the controlled comparison set out in Chapter 3, whose theory and technical background this chapter has now covered. A good result would support AI-GIS as a passive second detector or alert-ranking tool used alongside a firewall; a poor result would still be useful as evidence about the limits of the added model under these conditions. Either way, AI-GIS stays a human-governed research tool whose outputs need to be read by a person [34].

METHODOLOGY

This chapter describes what the researchers actually did. It covers how the dataset was built, how the data was cleaned and turned into model inputs, the three parts of AI-GIS, how the data was divided for training and testing, how ModSecurity was set up as the baseline, and how the two systems were compared. 3.1 Research Design

The study uses a quantitative, comparative experimental design [64]. The proposed model (AI-GIS) and a fixed rule-based web application firewall (ModSecurity with the OWASP Core Rule Set) each classify the same set of held-out records, and their results are compared using standard classification metrics [51], bootstrap confidence intervals [32], and a paired significance test [33]. Both systems run passively, so that every record is processed by both and neither blocks traffic during the experiment [37].

3.2 Dataset Acquisition and Corpus Construction

The training data is a labelled honeypot log built from WEB-IDS23 network-flow records. Instead of using raw benchmark strings on their own, the study generates attack payloads by family and places them on real flow metadata, then labels each record as attack (1) or benign (0). Building the corpus from documented attack families, rather than a small set of fixed strings, follows the finding that a model trained only on familiar payloads performs poorly on altered versions of the same attack [60]. Honeypot-derived and synthetic records are known to support controlled, repeatable datasets as long as they are checked for artefacts that could let a model take shortcuts [45]. This construction is carried out by a documented Python script and its companion notebook.

Code Snippet 3.1 — Attack payloads are generated by family, and every payload is kept unique (webids23_to_honeypot_log_v9.py).

seen = set()
def unique_payload(generator, rng, max_tries=25):
    for _ in range(max_tries):
        p = generator(rng)
        if p not in seen:
            seen.add(p); return p, False
    p = p + nonce(rng)               # last resort: append a short nonce
    seen.add(p); return p, True      # and flag the row: "forced_unique_nonce": true

The script also varies incidental fields on purpose. For example, it draws the user-agent string from a weighted list so that ordinary browser agents are common and tool agents such as sqlmap appear only rarely. This prevents the model from learning an easy but misleading shortcut, such as “the request came from a scanning tool, therefore it is an attack,” instead of learning the structure of the payload itself [45]. Each record is saved as one JSON line with its label, attack family, and provenance flags. The same steps are also available as a notebook (1_honeypot_generator.ipynb) so the dataset can be rebuilt exactly.

Corpus composition (as built). The honeypot log contains 36,364 base records, balanced at 18,182 attack and 18,182 benign, covering seven SQLi families (tautology, UNION-based, boolean-blind, time-based blind, error-based, stacked-query, authentication-bypass) and three XSS families (reflected, stored, DOM-based). To help the model tell real attacks apart from ordinary text that happens to look attack-like (source code, logs, shell commands, and mathematics), 428 curated benign records of this kind were added, giving 18,610 benign records for training.

3.3.1 Part One — Random Forest Branch (engineered features)

Purpose: summarise measurable properties of a payload. Input: the decoded request text. Processing: a 319-value feature vector is built — overall payload statistics, structural attack-pattern flags, and character n-gram weights [78] — and given to a Random Forest [25], [46]. Output: one probability that the request is malicious. Relationship: this probability is one of the two inputs to the meta-learner.

Code Snippet 3.2 — Building the aggregate features (prepare_honeypot_for_training.py).
def payload_text(row):
    uri  = row.get("uri", "")
    body = row.get("request_body", "") or ""
    query = uri.split("?", 1)[1] if "?" in uri else ""
    return f"{query} {body}".strip()

def engineer_rf_features(row, text):          # simple, interpretable counts [25]
    lower = text.lower()
    return {
        "payload_len": len(text),
        "entropy": shannon_entropy(text),
        "num_special_chars": sum(1 for c in text if not c.isalnum() and not c.isspace()),
        "num_digits": sum(c.isdigit() for c in text),
        "num_uppercase": sum(c.isupper() for c in text),
        "param_count": row.get("uri","").count("&") + (1 if "?" in row.get("uri","") else 0),
        "is_post": int(row.get("method","").upper() == "POST"),
        "has_sqli_keyword": int(any(k in lower for k in SQLI_KEYWORDS)),   # [22]
        "has_xss_keyword": int(any(k in lower for k in XSS_KEYWORDS)),     # [23]
        "quote_count": text.count("'") + text.count('"'),
        "comment_token_count": text.count("--") + text.count("/*") + text.count("#"),
    }

These simple counts are joined with structural pattern flags and a 300-term character n-gram TF-IDF representation [78] to make the full 319-value vector.

3.3.2 Part Two — LSTM Branch (character sequence)

Purpose: keep the order of characters and fragments. Input: the decoded payload. Processing: each character becomes a number, and the sequence is padded or cut to 200 positions; two LSTM layers [19], [47] read the sequence in order. Output: one probability per payload. Relationship: the second input to the meta-learner. As explained in Section 2.1.6, a masking step [79] is needed so the network ignores the empty padding positions.

Code Snippet 3.3 — Character encoding and the masked LSTM (18_train_stacked.py).
def ordinal_encode(text, max_len=200):
    arr = np.zeros(max_len, dtype=np.int32)          # 0 = padding
    for i, c in enumerate(text[:max_len]):
        code = ord(c)
        arr[i] = code if code <= 127 else 1          # 1 = unknown character [74]
    return arr

model = keras.Sequential([
    layers.Input(shape=(200,)),
    layers.Embedding(input_dim=128, output_dim=32, mask_zero=True),  # ignore padding [79]
    layers.LSTM(64, return_sequences=True),          # [47]
    layers.Dropout(0.3),
    layers.LSTM(32),
    layers.Dropout(0.3),
    layers.Dense(1, activation="sigmoid"),
])

3.3.3 Part Three — Logistic Regression Meta-Learner (stacking)

Purpose: decide how much to trust each branch. Input: the two branch probabilities, taken from the validation data so the meta-learner never sees the branches’ own training rows. Processing: a logistic regression [48] is fitted on these paired probabilities. Output: the final probability. Relationship: this is validation-based stacking [29], which stops the top layer from over-trusting the two branches.

3.4 ModSecurity Baseline and Its Link to AI-GIS

ModSecurity runs as a separate container using the OWASP Core Rule Set at Paranoia Level 2, with an inbound anomaly threshold of five, in DetectionOnly mode [37], [38], [76]. It is the study’s rule-based baseline. AI-GIS does not receive ModSecurity’s output, and ModSecurity does not receive AI-GIS’s. The two systems look at the same records on their own, and each makes its own decision. This independence is what makes the comparison fair: the question is how a learned model and a rule-based tool each perform on the very same inputs [37].

# Browser headers are used so the rule set judges the PAYLOAD, not the client [75].
# A record counts as detected if EITHER the GET query or the POST body is blocked (403).
def modsec_blocked(payload):
    for method in ("get", "post"):
        try:
            if method == "get":
                req = Request(HOST + "/get?q=" + quote(payload, safe=""), headers=BROWSER_HEADERS)
            else:
                req = Request(HOST + "/post", data=urlencode({"q": payload}).encode(),
                              headers={**BROWSER_HEADERS, "Content-Type": "application/x-www-form-urlencoded"})
            urlopen(req, timeout=15)
        except HTTPError as e:
            if e.code == 403:
                return True     # the anomaly score reached the threshold [75]
    return False

3.6 Dataset Division

The corpus is split by session rather than by row, using a grouped split so that no session appears in more than one part [77]. This avoids leakage: because one session can produce several very similar payloads, a row-level split could place near-duplicates in both training and testing and make the model look better than it is. The split is about 70% training, 15% validation, and 15% testing, a common and well-supported choice [64].

3.7 Training Procedure

The Random Forest is trained on the class-balanced training data [49], [50]; the LSTM is trained for up to eight passes over the data, keeping the checkpoint with the best validation score and stopping early if it stops improving [47]; and the logistic regression meta-learner is fitted on the validation-set probabilities of the two branches [29], [48]. A fixed random seed (42) is used throughout and the software environment is recorded, so the results can be reproduced [67], [68].

3.8 Comparative Evaluation Procedure

Both AI-GIS and ModSecurity classify the same held-out records. For AI-GIS, the final probability is compared against a 0.5 threshold; for ModSecurity, a record counts as detected when its anomaly score reaches the threshold and the request is blocked [75]. Because ModSecurity gives a yes/no answer and no continuous score, its AUC-ROC cannot be computed and is reported as undefined rather than invented [30]. Results are computed for the whole set and for the SQLi and XSS subsets, using Precision, Recall, F1-Score, False Positive Rate, and AUC-ROC [51]. Ninety- five-percent confidence intervals come from bootstrap resampling (1,000 rounds, seed 42) [32], [52], and McNemar’s exact test checks whether the two systems’ disagreements are meaningful [33], [53]. An ablation compares the full model against its individual parts on the same benchmark [29].

3.9 Software and Hardware Environment

The implementation uses Python with scikit-learn for the Random Forest, logistic regression, metrics, and resampling [46], [48], [51], [52]; TensorFlow and Keras for the LSTM [47], [79]; and pandas for data handling. CHAPTER 4
RESULTS AND DISCUSSION

The results in this chapter are the initial draft of the system and its evaluation. With more time to run, refine, and tune the model, the researchers expect the reported results to be updated and improved. These findings should be read as a first measure of how the system behaves, not as its final, best performance.

4.1 Experimental Setup

AI-GIS was trained on the constructed corpus using the session-based split described in Section 3.6, then tested, alongside the ModSecurity CRS PL2 baseline, on the same held-out benchmark of 1,000 obfuscated attacks (600 SQLi, 400 XSS) and 700 unseen benign records. AI-GIS decisions use a 0.5 probability threshold; ModSecurity runs in DetectionOnly mode and blocks a request when its anomaly score reaches five [75]. Confidence intervals are bootstrap estimates (1,000 rounds, seed 42) [32], [52], and paired significance uses McNemar’s exact test [33], [53].

Each of the following sections is organised around one Statement of the Problem (SOP) and reports the result that answers it, along with the Research Question (RQ) and Research Objective (RO) it maps to. Table 4.6 summarises this mapping at the end of the chapter.

The shuffled-label check is the important one: a model relying on a hidden shortcut would still score highly with random labels, but AI-GIS drops to chance (AUC 0.505). This means the detection results below reflect a real learned signal. It also means the training corpus is easy to separate, which is why the main evaluation uses the harder held-out benchmark rather than the internal test split.

4.5 SOP1 — Comparison with a Rule-Based WAF (answers RQ3, meets RO3)

Problem. It is unclear whether a fixed rule-based firewall reliably detects changed attacks without also blocking legitimate traffic. Result. Table 4.4 compares AI-GIS and ModSecurity on the same records.

Discussion. ModSecurity caught marginally more attacks (99.8% vs 97.9%) but blocked 90.1% of legitimate requests, which dropped its precision to 0.613 and its F1 to 0.759 — below the 0.75 target and well below AI-GIS’s 0.925. This happens because, at the paranoia level needed to catch changed attacks, the rule set also flags ordinary traffic that looks similar [75]. On the paired records, AI-GIS was right where ModSecurity was wrong in 496 cases, against 21 the other way; McNemar’s test gives p ≈ 6.1×10-119, so the difference is statistically real, not chance [33]. This answers RQ3 and meets RO3: AI-GIS does not beat the firewall at raw detection, but it is far better overall because it does not drown the analyst in false alarms, supporting its use as a complementary detector alongside a WAF [34]. One caveat: the benign set was chosen to look attack-like on purpose, which raises the false-positive rate of both systems; the reliable finding is the large gap between them, not the exact numbers.

Problem. A single method may not be enough, which is why the model stacks two branches. This section tests whether stacking actually helps [29]. Result. Table 4.5 shows the model with parts removed.

Discussion. On this benchmark the full stacked model (F1 0.925) does not beat the Random Forest on its own (0.957), and the best result comes from the Random Forest plus the meta-learner without the LSTM (0.974). The LSTM is the weaker branch here and drags the combined result down. Under the rule set before the experiment, this means stacking does not add value on this data [29]. This is reported honestly rather than hidden. A likely reason is that the benchmark payloads are short, and the sequence branch is expected to help more on longer payloads, so this result is specific to the current data and is carried forward for re-testing.

4.8 Limitations and Next Steps

These results are bounded as follows. The false-positive rate is measured on benign text chosen to look attack-like, so it is a worst case; the ablation result depends on the current benchmark and its short payloads; and the ModSecurity comparison, though run on the same records and a documented configuration, reflects this first evaluation. In line with the note at the start of this chapter, these values set the system’s starting point, and further running and tuning are expected to improve them.
