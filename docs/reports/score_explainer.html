How good is the detector, really?

A plain-language guide to every score the system reports — what each number means, which ones to trust, and where the model still fails when a fresh AI attacks it.

False alarms on normal text
57.6% → 2.5%
After retraining on harder examples · 5 of 198 benign sentences flagged
Attacks caught
93.9% → 95.5%
Both numbers improved together — no trade-off

The headline is the honest story: the detector went from flagging more than half of ordinary, symbol-heavy text as attacks, to flagging 1 in 40 — while also catching slightly more real attacks. The rest of this page explains how those numbers are produced and why the more impressive-looking scores elsewhere mean less than they appear to.

01The two numbers that matter

Every score in this system reduces to two questions, and they pull against each other:

  • Detection rate — of the real attacks, how many did it catch? Higher is better. Missing an attack is a false negative.
  • False-positive rate (FPR) — of the harmless text, how much did it wrongly flag? Lower is better. A false alarm on a real user is a false positive.

A detector that flags everything catches 100% of attacks — and is useless, because it also blocks every real user. So neither number means anything alone. They are only meaningful together, and the whole craft is pushing both the right way at once.

Why "F1" and "AUC" appear too

F1 blends precision and recall into one number (1.0 is perfect). AUC-ROC measures how well the model ranks attacks above benign text, independent of the cut-off (1.0 is perfect, 0.5 is a coin flip). They're useful summaries — but on this project they're mostly pinned at 1.0, which is itself a warning sign. See section 3.

02The test that actually counts

Numbers are only as honest as the data they're measured on. The trustworthy figures on this page come from a hold-out set of 396 sentences — 198 real attacks and 198 harmless-but-tricky ones (code snippets, file paths, regexes, math, names like O'Brien) — that the model never saw during training. That last part is what makes the number real: the model can't have memorised the answers.

This is the case for the stacked design in one row: the Random Forest catches everything but cries wolf often (6.1%); the LSTM is calm but misses more attacks; stacking gives you the LSTM's low false-alarm rate with almost the RF's coverage. That combination is the contribution.

03Why 100% accuracy is a red flag, not a trophy

Elsewhere the system reports F1 = 1.0 and AUC = 1.0 on its main test set. That looks spectacular. It should make you suspicious instead — and here's the concrete evidence, straight from the system's own statistics.

The bootstrap confidence interval is zero-width

Resampling the test set 1,000 times, the ensemble's false-positive rate came back 0.0000 every single time — interval [0.0, 0.0]. A real-world detector does not do that. It means the test set is saturated: the synthetic attacks and synthetic benign traffic are so cleanly separable that every decent model scores perfectly, so the test can no longer tell good models apart.

The statistical tests confirm it. McNemar's test asks whether two models disagree enough to call one genuinely better:

McNemar's test on the hold-out set · α = 0.05
ComparisonDisagreements (b / c)p-valueVerdict
Stacked vs Random Forest1 / 60.131Not significant
Stacked vs LSTM5 / 10.221Not significant

Both p-values are above 0.05, so the honest claim is not "the ensemble is significantly better." It's this: stacking does not degrade clean performance while it improves robustness on the hard cases — and the models barely disagree because the test set is too easy to separate them. Say that in the thesis; it's defensible and the numbers back it. The ablation study agrees: the only condition that visibly drops is plain logistic regression on 11 hand-counted features (F1 0.984), which is the evidence that the engineered features earn their place.

04What happens when a fresh AI attacks it

The cleanest test of a detector is to point a different AI at it and have it write novel evasions — attacks the model has never seen, plus harmless text designed to look dangerous. Two rounds were run this way. The pattern in the failures is the whole story.

Harder than the hold-out set, deliberately. But look at which cases fail — they all share one root cause.

Attacks that slipped through

Harmless text it wrongly flagged

JSON {"user": "admin", "query": "SELECT * FROM t", "ok": true} Symbol-dense and contains the word SELECT — flagged despite being an ordinary API payload. 0.994false alarm

The one-sentence diagnosis

The model is an excellent detector of character patterns, and not a detector of intent. It catches obfuscated attacks brilliantly as long as they keep their punctuation, and it panics at innocent text that happens to be punctuation-heavy. Every failure above is one face of that single fact.

05The comparison that matters: vs. a real firewall

A detection score means little without something to compare against. So the same inputs were fired through ModSecurity + the OWASP Core Rule Set — the industry-standard open-source web-application firewall — running live in a container at paranoia level 2. This is the "versus" that turns a result into a contribution.

Same clean traffic through both systems · ModSecurity fired as ~5,800 live HTTP requests
MetricModSecurity + CRSAI-GIS Stacked
False-positive rate32.8%2.5%
False alarms (count)895 / 2,7335 / 198
Attack detection~100%95.5%
Hard-benign false alarms8 / 151 / 8

This is the headline result for the thesis

ModSecurity catches essentially every attack — but flags one in three legitimate requests as an attack (895 of 2,733). The ensemble reaches comparable detection at a ~13× lower false-alarm rate. "We match a production firewall's detection while cutting its false alarms thirteen-fold" is a far stronger, and fully external, claim than any accuracy figure. The firewall's high false-alarm rate is the real, well-known cost of signature-based blocking — and the gap the learned model is designed to close.

Measured with owasp/modsecurity-crs:nginx, paranoia level 2, inbound anomaly threshold 5. ModSecurity returns a binary block/allow (HTTP 403 / 200), so it has no probability score — its "AUC" equals accuracy and isn't directly comparable to the model's ranked AUC.

06How to read all this for the thesis

  • Open with the ModSecurity comparison. "13× fewer false alarms than the standard WAF at comparable detection" is the single strongest, most defensible sentence in the whole project.
    • Lead with the false-alarm improvement, not the perfect scores. "We cut false alarms from 57.6% to 2.5% with no loss of detection" is a real, defensible contribution. "100% accuracy" invites the examiner to attack the data.
    • Present 100% as a sanity check, not a result. State plainly that the synthetic test set is saturated, and that the meaningful separation lives in the hold-out and adversarial sets.
    • Don't claim statistical superiority for stacking — the p-values don't support it. Claim robustness-without-regression, which they do.
    • Turn the failures into future work. Natural-language and full-hex evasion, plus false alarms on JSON/XML — these are specific, explainable, and honest. A committee rewards a known, bounded weakness over a suspicious clean sweep.
