This guide outlines the precise steps required to configure the external dependencies for the final phases of your thesis: generating the adversarial LLM payload corpus and establishing the ModSecurity baseline.

Phase 1: Ollama Setup (WSL2 Debian)

You already have Ollama installed in WSL2. We need to ensure the correct models are pulled and that the API is accessible to your Windows-side Python pipeline.

1. Pull the Required Models

In your WSL2 Debian terminal, download the models specified in Chapter 3:

ollama run codellama:13b
ollama run deepseek-r1:14b

(Press Ctrl+D to exit the prompt once downloaded).

2. Configure API Access (Crucial)

By default, Ollama in WSL2 binds to 127.0.0.1 inside the Linux VM, making it unreachable from your Windows host where the Python scripts run. We need to bind it to all interfaces.

Edit the Ollama service configuration in Debian:

sudo mkdir -p /etc/systemd/system/ollama.service.d
echo '[Service]' | sudo tee /etc/systemd/system/ollama.service.d/override.conf
echo 'Environment="OLLAMA_HOST=0.0.0.0:11434"' | sudo tee -a /etc/systemd/system/ollama.service.d/override.conf

sudo systemctl daemon-reload
sudo systemctl restart ollama
✅
Verification: Open PowerShell on Windows and run curl http://localhost:11434/api/tags. It should return a JSON list of your installed models.

Phase 2: ModSecurity + OWASP CRS Baseline

We will use Docker Desktop on Windows (using the WSL2 backend) to spin up the official OWASP CRS Nginx container. This ensures an air-gapped, reproducible environment.

1. Pull the Official Stable Image

In PowerShell, pull the stable v4 CRS image:

docker pull owasp/modsecurity-crs:4-nginx

2. Prepare the Evaluation Script

We need a Python script to throw the `rf_test_v2.csv` payloads at the ModSecurity container and record whether it returns a 200 OK (passed) or 403 Forbidden (blocked). Since ModSecurity is a WAF, it evaluates HTTP requests, not CSV rows. The script will format the payloads as HTTP GET/POST requests.

3. Run the Container in Anomaly Scoring Mode (Paranoia Level 2)

Your Chapter 3 methodology specifies Paranoia Level 2 (PL2). Start the container with the required environment variables in PowerShell:

docker run -d `
  --name modsec-baseline `
  -p 8080:80 `
  -e PARANOIA=2 `
  -e ANOMALY_INBOUND=5 `
  -e ANOMALY_OUTBOUND=4 `
  owasp/modsecurity-crs:4-nginx
Why Anomaly Scoring? Modern ModSecurity doesn't block on the first matched rule. It adds anomaly points. Setting ANOMALY_INBOUND=5 ensures that if the score reaches 5 (usually 1 critical rule or 2 minor rules), the request is blocked (HTTP 403).
✅
Verification: In PowerShell, test a benign request: curl http://localhost:8080/ (Should return 200 OK or 502/404 depending on backend, but NOT 403). Then test an attack: curl http://localhost:8080/?q=1%27%20OR%20%271%27%3D%271 (Should return 403 Forbidden).
